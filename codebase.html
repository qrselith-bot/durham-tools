The DOM: Selecting and Changing Things

Every tool you've built, the tab bars, checklists, search boxes, modals, all come down to the same handful of moves. This lesson names those moves, then shows you exactly where they live in your own knowledge base tool.

Fundamentals

What the DOM actually is

When a browser loads your HTML, it doesn't just display the text, it builds a live structure in memory called the DOM (Document Object Model). Every tag becomes an object your JavaScript can reach into, read, and change. HTML is the blueprint; the DOM is the actual building, and JavaScript is what walks around inside it flipping switches.

Selecting an element

Before you can change anything, you have to grab it. Two ways show up constantly in your code:

document.getElementById('search') grabs the one element with that exact id. Fast, and works because every id on a page is meant to be unique.

document.querySelectorAll('.tab') grabs every element with that class, as a list. Use this when you want to do the same thing to several elements at once.

Changing what's there

Once you have an element, the property you touch most is classList. It doesn't change what an element says, it changes which CSS rules apply to it. classList.add(), .remove(), and .toggle() are how almost every visual state change in your tools happens: active tabs, checked boxes, open panels. The JavaScript never decides what "active" looks like, it just decides whether the class is present. The look lives entirely in your CSS.

Doing it for a whole list at once

.forEach() walks through a list and runs the same function on every item. You'll see this pattern constantly: a short array of names or ids, followed by a forEach that does one repeatable action per item. It's the difference between writing six near-identical lines and writing one line that scales to any number of items.

Responding to a click

Two patterns show up in your code for this, and it's worth knowing both: onclick="functionName()" written directly in the HTML, and element.addEventListener('click', function(){...}) attached in JavaScript. Both work. The inline version is quicker to write and read for small tools like yours; addEventListener is the more scalable pattern for anything that gets complex or needs multiple listeners on the same element.

Applications — from durham_knowledge_base.html

Tab switching

function switchTab() 
var PANELS = ['authority','scenarios','checklists','procedures','rooms','contacts'];

function switchTab(id, btn) {
  PANELS.forEach(function(p) {
    document.getElementById('p-'+p).classList.toggle('active', p === id);
  });
  document.querySelectorAll('.tab').forEach(function(t) {
    t.classList.remove('active');
  });
  if (btn) btn.classList.add('active');
}
PANELS.forEach(...)
Walks every panel name. For each one, checks whether it matches the tab that was clicked.
classList.toggle('active', p === id)
The second argument turns toggle from a flip into a direct set: true when this panel is the match, false otherwise. One line replaces what would be six if/else blocks.
querySelectorAll('.tab').forEach(...)
Same move, applied to the tab buttons themselves, so the highlight follows the click.
Why it's built this way: Add a 7th panel later and you only add one string to PANELS. No new logic. Whenever you see a short array feeding a forEach, that's usually a sign the code was built to grow.

Checklist item toggle

function chk(el) 
function chk(el) {
  el.classList.toggle('done');
}
el.classList.toggle('done')
No second argument here, so this really does flip: adds "done" if it's missing, removes it if it's present.
Why it's built this way: This is the smallest possible version of the pattern. One line, one job. Everything you see happen visually, the checkmark, the strikethrough, the faded text, is CSS reacting to the presence of .done. The function never touches appearance directly.

Accordion / scenario expand

function tog(header) 
function tog(header) {
  var body = header.nextElementSibling;
  var chev = header.querySelector('.chev');
  var isOpen = body.classList.contains('open');
  body.classList.toggle('open', !isOpen);
  body.style.display = isOpen ? 'none' : 'block';
  if (chev) chev.classList.toggle('open', !isOpen);
}
header.nextElementSibling
Instead of an id lookup, this grabs whatever HTML element sits directly after the header in the page's structure. That's how it finds "the body that belongs to this specific header" without needing a matching id pair.
classList.contains('open')
Checks current state before deciding what to do next, rather than assuming.
isOpen ? 'none' : 'block'
A ternary: shorthand for a two-line if/else that picks one of two values.
Why it's built this way: Using nextElementSibling instead of ids means you can duplicate a whole scenario block in the HTML and it just works, no id renaming required. It does mean the HTML order matters: the body has to come immediately after its header.

Clearing a form before it opens

function openConModal() 
function openConModal() {
  ['c-role','c-name','c-det','c-notes'].forEach(function(id) {
    document.getElementById(id).value = '';
  });
  document.getElementById('con-modal-bg').classList.add('open');
  document.getElementById('c-role').focus();
}
['c-role','c-name',...].forEach(...)
Same array-plus-forEach pattern as PANELS, this time used to blank out four input fields in one pass instead of four separate lines.
.focus()
Moves the cursor straight into the first field, so whoever opened the modal can start typing immediately.
Why it's built this way: Same principle as the tab list: a short array of ids is easier to extend than a wall of repeated lines. Recognizing this shape once means you recognize it everywhere in your code from here on.
